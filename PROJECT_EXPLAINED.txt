===============================================================================
        FOOD DELIVERY DATA WAREHOUSE — COMPLETE PROJECT EXPLANATION
===============================================================================

This document explains the entire project from top to bottom, in plain
language. You do NOT need to be a data expert to follow it. Every technical

===============================================================================
PART 0 — THE BIG PICTURE (READ THIS FIRST)
===============================================================================

Imagine a food delivery company like Uber Eats, Deliveroo, or Swiggy.
Every single day, thousands of things happen:
   - Customers place orders.
   - Restaurants prepare food.
   - Delivery agents pick up and deliver meals.
   - Payments are made.

All of this activity produces DATA — records of who ordered what, when, from
which restaurant, delivered by whom, and for how much money.

The company's managers want to answer questions like:
   - "Which restaurants made the most money last month?"
   - "How many orders did we get in June?"
   - "What is the average order value this year compared to last year?"

To answer these questions quickly and reliably, the company needs a
DATA WAREHOUSE.

WHAT IS A DATA WAREHOUSE?
------------------------
A data warehouse is a large, organized, central database built specifically
for ANALYSIS and REPORTING (not for running the day-to-day app).

Think of it like this:
   - The mobile app uses a fast "operational" database to take orders in
     real time. That database is optimized for speed, not for analysis.
   - The data warehouse is a separate place where all that data is COPIED,
     CLEANED, and REORGANIZED so managers and analysts can ask big questions
     and get answers fast.

This project builds that data warehouse — plus all the automated "plumbing"
that feeds it — for a fictional food delivery company.

The warehouse itself lives in a cloud platform called SNOWFLAKE.

WHAT IS SNOWFLAKE?
------------------
Snowflake is a cloud data warehouse. "Cloud" means it runs on the internet
(on rented servers), not on your own computer. You send it data and questions
(written in a language called SQL), and it stores the data and answers the
questions. It is one of the most popular tools in the data industry.

WHAT IS SQL?
------------
SQL (Structured Query Language) is the language used to talk to databases.
With SQL you can create tables, load data into them, and ask questions like
"give me the total revenue for 2024." Almost every database in the world
understands SQL.

PART 1 — HOW THE DATA IS ORGANIZED: THE "MEDALLION" ARCHITECTURE
===============================================================================

Raw data from the real world is messy. If you pour messy data straight into
your final reports, the reports will be wrong. So the data is cleaned in
STAGES, moving from messy to perfect.

This staged approach is called the MEDALLION ARCHITECTURE. It has three
layers, often nicknamed Bronze, Silver, and Gold — like Olympic medals,
where Gold is the best/most refined.

In Snowflake, each layer is a separate SCHEMA. A SCHEMA is simply a folder
inside the database that groups related tables together. This project has
these schemas:

   1. BRONZE LAYER  →  schema called "stage_sch"    (raw, untouched data)
   2. SILVER LAYER  →  schema called "clean_sch"    (cleaned, typed data)
   3. GOLD LAYER    →  schema called "consumption_sch" (final, ready for reports)

   (There is also a fourth schema, "common", which holds shared security
    rules — explained later.)

Let's go through each layer.

-------------------------------------------------------------------------------
LAYER 1 — BRONZE ("stage_sch"): THE LANDING ZONE
-------------------------------------------------------------------------------
This is where raw data files first arrive. The company's source systems
produce CSV files.

WHAT IS A CSV FILE?
A CSV (Comma-Separated Values) file is a simple text file that holds a table.
Each line is a row, and commas separate the columns. It's like a spreadsheet
saved as plain text. Example:
   customer_id,name,city
   1,Ahmed,Rabat
   2,Sara,Casablanca

In the Bronze layer, the data is loaded EXACTLY AS IT ARRIVES — no cleaning.
A very important design choice here: every column is stored as TEXT.

WHY STORE EVERYTHING AS TEXT?
Because raw data is unpredictable. Suppose a price column should contain a
number like "10", but by mistake a source system writes the word "Ten".
If the column expected a number, loading would CRASH and the whole day's data
import would fail. But if the column accepts any text, "Ten" loads without
crashing. We keep the bad value, flag it, and fix it in the next layer.
This makes the loading process robust — it never breaks.

Each Bronze table also has extra "audit" columns added automatically:
   - which file the row came from
   - when the file was loaded
   - a fingerprint (hash) of the file's content
These help with tracing and debugging: months later you can ask "where did
this strange row come from?" and get an exact answer.

-------------------------------------------------------------------------------
LAYER 2 — SILVER ("clean_sch"): THE CLEANING ZONE
-------------------------------------------------------------------------------
Here the messy Bronze data is transformed into clean, correct data.

The main jobs done in this layer:
   - CONVERT DATA TYPES: text "10" becomes the actual number 10; text
     "2024-06-15" becomes a real date/timestamp. This is called "casting".
   - HANDLE ERRORS SAFELY: a special function called TRY_CAST is used. Normal
     conversion crashes on bad data; TRY_CAST instead turns bad values into
     "empty" (NULL) and keeps going. So one bad row never stops the process.
   - REMOVE DUPLICATES: if the same record was loaded twice, only one copy
     is kept.

After the Silver layer, the data is trustworthy and properly typed, but still
organized simply (one clean table per real-world thing: customers, orders,
restaurants, etc.).

-------------------------------------------------------------------------------
LAYER 3 — GOLD ("consumption_sch"): THE BUSINESS ZONE
-------------------------------------------------------------------------------
This is the final, polished layer that analysts and dashboards actually use.
Here the clean data is reorganized into a special shape called a STAR SCHEMA,
which makes analytical questions extremely fast to answer.

WHAT IS A STAR SCHEMA?
It is a way of arranging tables into two types: FACTS and DIMENSIONS. When
you draw it, one central table connects out to several surrounding tables,
forming a shape like a star.

   FACT TABLE (the center of the star):
      Stores the measurable EVENTS — the "what happened" and "how much".
      In this project, the fact table is about order items: each row records
      an item that was ordered, with numbers like quantity, price, subtotal.
      Fact tables have MANY rows (one per event) and lots of numbers.

   DIMENSION TABLES (the points of the star):
      Store the DESCRIPTIVE CONTEXT — the "who, what, where, when".
      Examples: the customer dimension (who ordered), the restaurant
      dimension (from where), the location dimension (which city), the date
      dimension (which day/month/year). Dimensions have fewer rows and lots
      of descriptions.

HOW FACTS AND DIMENSIONS CONNECT:
The fact table doesn't repeat all the descriptive text. Instead, each fact
row stores small ID codes (called "keys") that POINT TO the matching row in
each dimension. So a fact row says, in effect: "order item #500, quantity 2,
price 180, customer=key123, restaurant=key456, date=key789." To get the full
picture you JOIN (connect) the fact to the dimensions using those keys.

This design is powerful because you compute the descriptive stuff once (in the
dimensions) and reuse it across millions of fact rows.

SPECIAL FEATURE — SLOWLY CHANGING DIMENSIONS (SCD TYPE 2):
Real-world descriptive data changes over time. A restaurant might move to a
new address. A delivery agent might relocate to a new city.

If you simply overwrite the old value with the new one, you LOSE HISTORY —
and your old reports become wrong (a delivery made last year would suddenly
appear to have come from the new city).

SCD Type 2 solves this by keeping BOTH versions:
   - The old record is "closed" with an end-date and marked "not current".
   - A new record is added with a start-date and marked "current".
So the same restaurant can have several historical rows, each valid for a
certain time period. Past reports stay correct; new reports use the new info.
This project uses SCD Type 2 for its dimensions.

THE DATE DIMENSION — A CLEVER TRICK:
Time-based analysis (by day, month, quarter, year) is extremely common. So the
project builds a DATE DIMENSION: a table with ONE ROW FOR EVERY SINGLE DAY,
from the very first order up to today. Each row is pre-filled with useful
details about that day: its year, quarter, month, week, day-of-week, day name,
etc. Any fact can then join to this table by date and instantly be grouped by
any time period. It is generated automatically using a "recursive" query — a
query that repeats itself, going back one day at a time until it reaches the
earliest order date, and stopping there.


===============================================================================
PART 2 — THE TOOLS THAT MOVE AND TRANSFORM THE DATA
===============================================================================

Building the layers requires machinery. Here are the key Snowflake tools used,
each explained simply.

COPY INTO — THE BULK LOADER
   The command that reads raw CSV files and loads their rows into Bronze
   tables. Think of it as a powerful vacuum that sucks data out of files and
   into the database.

FILE FORMAT — THE READING INSTRUCTIONS
   A small saved definition that tells Snowflake HOW to read the CSV files:
   the separator is a comma, skip the first row (the header), text may be
   wrapped in quotes, etc.

STAGE — THE LANDING AREA FOR FILES
   A "stage" is a storage location where files sit before being loaded into
   tables. There are two kinds:
      - INTERNAL stage: files stored inside Snowflake itself.
      - EXTERNAL stage: a POINTER to files stored OUTSIDE Snowflake (for
        example in Azure cloud storage). Snowflake can read them without
        moving them.

STREAM — THE CHANGE TRACKER (Change Data Capture / CDC)
   A "stream" watches a table and records WHAT CHANGED since you last looked
   (new rows inserted, rows updated or deleted). This lets the pipeline
   process ONLY the new/changed data ("the delta") instead of reprocessing
   everything every time — which saves a lot of computing cost. Important
   detail: once you "consume" (use) a stream's changes, it resets and starts
   tracking fresh. So the pipeline steps must run in the right order.

MERGE — THE SMART UPDATER (the "upsert")
   MERGE compares incoming data with existing data and does the right thing
   for each row:
      - if the record already exists → UPDATE it,
      - if it's new → INSERT it.
   This combined update-or-insert behavior is nicknamed "upsert". It's how
   data moves cleanly from one layer to the next without creating duplicates.

TAGS and MASKING POLICIES — THE SECURITY GUARDS (for PII)
   PII means "Personally Identifiable Information" — sensitive personal data
   like a customer's phone number.
      - A TAG is a label you stick on a column to say "this is sensitive".
      - A MASKING POLICY is a rule that hides the real value. For example,
        instead of showing a real phone number, unauthorized users see
        "** PII **".
   When a masking policy is linked to a tag, ANY column carrying that tag is
   automatically hidden from unauthorized users — protecting privacy without
   changing the stored data itself.


===============================================================================
PART 3 — TWO APPROACHES TO BUILDING THE SAME PROJECT
===============================================================================

This is the most important part to understand. The project was built in TWO
different ways that produce the SAME data warehouse. The first is the "manual"
learning version. The second is the "professional, automated" version. Keeping
both shows a clear progression from understanding the fundamentals to applying
industry-standard tooling.

The two approaches share the same destination (Snowflake) and the same
medallion architecture (Bronze → Silver → Gold). What differs is HOW the data
gets loaded and transformed, and how much of it is AUTOMATED.


-------------------------------------------------------------------------------
APPROACH 1 — THE MANUAL VERSION (built first, to learn the fundamentals)
-------------------------------------------------------------------------------
In this version, everything is done BY HAND using SQL scripts, run one by one
inside Snowflake's web interface (called Snowsight).

How it works, step by step:
   1. The person manually UPLOADS the CSV files into Snowflake's INTERNAL
      stage (dragging files into the web interface).
   2. They run a "01 Create DB + Schema" script to build the database,
      schemas, warehouse, file format, tags, and masking policies.
   3. For each entity (location, restaurant, customer, orders, etc.), they run
      a script that:
         - loads the raw file into the Bronze table (COPY INTO),
         - cleans and types it into the Silver table (MERGE + TRY_CAST),
         - builds the Gold dimension with SCD Type 2 history (a long,
           hand-written MERGE statement).
   4. They run a script to build the DATE DIMENSION (the recursive query).
   5. They run a script to build the FACT TABLE (joining clean transactional
      tables to the dimensions to fetch their keys).
   6. They run a script to create the KPI VIEWS (saved queries that calculate
      revenue totals, order counts, averages, etc.).

Characteristics of the manual approach:
   - You must run each script yourself, IN THE CORRECT ORDER. If you run them
     out of order, the streams empty out and data goes missing.
   - The SCD Type 2 logic is written by hand as long, complex MERGE statements
     (often 100+ lines each).
   - There are NO automated data-quality tests, NO automatic documentation,
     and NO automatic ordering of steps.
   - It is perfect for LEARNING because you see and control every single step.
     But it is slow, error-prone, and not how large teams work in production.

The manual SQL scripts (kept in the repository as "snowflake_scripts") are:
   01_create_db_schema, 02_location_entity, 03_restaurant_entity,
   04_customer_entity, 05_customer_address_entity, 06_menu_entity,
   07_delivery_agent_entity, 08_delivery_entity, 09_orders_entity,
   10_order_item_entity, 11_date_dim, 12_order_item_fact, 13_kpi_views,
   14_azure_load, and 15_azure_integration_setup.


-------------------------------------------------------------------------------
APPROACH 2 — THE AUTOMATED, PROFESSIONAL VERSION (built second)
-------------------------------------------------------------------------------
This version rebuilds the SAME warehouse, but replaces manual work with
industry-standard tools so that the whole pipeline runs BY ITSELF, on a
schedule, with no human clicking buttons. It uses FOUR key technologies:
Terraform, Azure, dbt, and dbt Cloud, tied together by Azure Data Factory.

Let's understand each one and how they fit together.

(A) TERRAFORM — INFRASTRUCTURE AS CODE
   In the manual version, you create the database, schemas, and warehouse by
   clicking and running SQL. In the professional version, you DESCRIBE all
   that infrastructure in code files (".tf" files), and Terraform builds it
   for you automatically.

   WHAT IS "INFRASTRUCTURE AS CODE" (IaC)?
   It means your cloud setup (databases, storage, compute) is defined in text
   files that can be saved, version-controlled, reviewed, and re-run. If you
   ever needed to rebuild everything from scratch, you'd run one command
   instead of clicking through menus for hours.

   Terraform talks DIRECTLY to the platforms through "providers" (plugins).
   In this project Terraform manages TWO platforms at once:
      - Snowflake (the database, schemas, warehouse, storage integration),
      - Azure (the cloud storage and the Data Factory service).
   This makes the whole environment reproducible and professional. It is a
   highly valued skill.

(B) AZURE — THE CLOUD STORAGE "DATA LAKE" LANDING ZONE
   In the manual version, files are uploaded straight into Snowflake. In the
   professional version, files first land in AZURE cloud storage, and
   Snowflake reads them from there.

   WHAT IS AZURE?
   Azure is Microsoft's cloud platform (a competitor to Amazon AWS and Google
   Cloud). This project uses Azure's storage service to hold the raw CSV files.

   Key Azure pieces created (via Terraform):
      - A RESOURCE GROUP: a folder that holds all the Azure resources together.
      - A STORAGE ACCOUNT (specifically "ADLS Gen2" — Azure Data Lake Storage,
        optimized for analytics): the storage service itself.
      - A CONTAINER (named "raw"): a folder inside the storage account where
        the CSV files actually sit. (In Amazon's world this is called a
        "bucket"; Azure calls it a "container". A single file inside it is
        called a "blob".)

   WHY PUT FILES IN AZURE INSTEAD OF STRAIGHT INTO SNOWFLAKE?
   This follows the standard "data lake" pattern used by real companies:
      - It SEPARATES storage from compute: the cheap raw files live in Azure,
        independent of the warehouse. You keep the originals even if Snowflake
        tables are rebuilt.
      - It's CHEAPER to store large amounts of raw data in object storage than
        inside the warehouse.
      - It's more FLEXIBLE: multiple tools could read the same files, not just
        Snowflake.
      - It uses a SECURE connection (see next point) instead of manual uploads.

   THE SECURE CONNECTION — "STORAGE INTEGRATION":
   For Snowflake to read the Azure files, the two platforms must TRUST each
   other — WITHOUT storing any password. This is set up in three moves:
      1. A "storage integration" object is created in Snowflake. This makes
         Snowflake generate its own secret identity (like an ID badge).
      2. You visit a special "consent" link that registers Snowflake's
         identity into your Azure account (adding it to Azure's guest list).
      3. You grant that identity permission to READ the storage container.
   After that, Snowflake can securely read Azure files with no password saved
   anywhere. An EXTERNAL STAGE (a pointer, described earlier) is then created
   so Snowflake can list and load those Azure files.

(C) dbt — THE TRANSFORMATION FRAMEWORK
   This is the biggest upgrade over the manual approach. In the manual version,
   you write and run all the transformation SQL by hand, in order. dbt
   ("data build tool") automates and organizes all of that.

   WHAT DOES dbt DO, EXACTLY?
   dbt does NOT store any data and does NOT replace Snowflake. Snowflake still
   holds all the data and does all the actual work. dbt is the "head chef" that
   organizes the recipes: it takes your transformation SQL, figures out the
   correct order to run everything, sends the SQL to Snowflake to execute, and
   adds testing and documentation on top.

   The transformation logic that was manual SQL becomes dbt "MODELS". A MODEL
   is simply a file containing one SELECT query; dbt turns each model into a
   table or view in Snowflake. Models reference each other using a special
   "ref()" function, and from those references dbt AUTOMATICALLY works out the
   dependency order (staging first, then clean, then gold) — so you never again
   run scripts in the wrong order.

   In this project the models are organized as:
      - STAGING models (views): lightly rename the raw columns.
      - CLEAN models (tables): apply data types, TRY_CAST, and remove
        duplicates.
      - MART models (the gold layer): the fact table and the KPI views.

   dbt's THREE BIGGEST WINS over the manual version:
      1. SNAPSHOTS replace the hand-written SCD Type 2 MERGEs. A "snapshot" is
         a dbt feature that automatically tracks dimension history (the
         start-date, end-date, current-flag logic). What took 100+ lines of
         manual MERGE per dimension becomes about 10 lines of configuration.
      2. TESTS check data quality automatically on every run — for example,
         verifying that key columns are never empty (not_null) and never
         duplicated (unique). If bad data appears, dbt catches it immediately
         instead of letting wrong numbers reach the dashboard.
      3. DOCUMENTATION and LINEAGE are generated for free: dbt produces a
         browsable documentation site including a LINEAGE GRAPH — a visual
         diagram showing how data flows from raw sources through every model to
         the final outputs. Great for understanding and for demos.

(D) dbt CLOUD — RUNNING dbt AUTOMATICALLY
   Running dbt on your own computer is fine for development, but automation
   needs dbt to run "in the cloud" so other tools can trigger it. dbt CLOUD is
   the hosted version of dbt. It reads the project's code from GitHub (a
   website that stores code and tracks its history), connects to Snowflake, and
   can run the whole pipeline either on a schedule or when triggered by an API.

   WHAT IS AN API?
   An API (Application Programming Interface) is a way for one program to send
   a command to another program over the internet. Here, Azure Data Factory
   uses dbt Cloud's API to say "run the pipeline now".

(E) AZURE DATA FACTORY (ADF) — THE ORCHESTRATOR THAT TIES IT ALL TOGETHER
   ADF is Azure's orchestration and data-movement service. It is the conductor
   of the whole automated pipeline. It runs a sequence of steps in order:

      STEP 1 — COPY: ADF copies the raw CSV files from the local computer into
               the Azure "raw" container. Because the source files are on a
               local machine, ADF uses a small helper program installed on that
               machine called a SELF-HOSTED INTEGRATION RUNTIME (SHIR) — think
               of it as a secure bridge that lets the cloud reach local files.

      STEP 2 — SCRIPT (COPY INTO): ADF then runs SQL on Snowflake (through a
               Snowflake connection) that loads the Azure files into the Bronze
               stage tables. (COPY INTO automatically skips files it has already
               loaded, so re-running never creates duplicates.)

      STEP 3 — WEB (trigger dbt): ADF calls dbt Cloud's API, which runs the
               full dbt pipeline (staging → clean → marts, with snapshots and
               tests). Only AFTER the load step succeeds does dbt run — so dbt
               always works on fresh data. This ordering is enforced by
               connecting the steps with "on success" arrows.

   These three steps are chained: COPY → SCRIPT → WEB.

   THE SCHEDULE TRIGGER — TRUE HANDS-FREE AUTOMATION:
   Finally, a SCHEDULE TRIGGER is attached to the ADF pipeline so the whole
   chain runs automatically every hour (or any chosen interval), with no human
   involvement. Each run: copies any new files to Azure, loads them into
   Snowflake, and rebuilds the warehouse via dbt.


===============================================================================
PART 4 — THE FINAL RESULT: THE DASHBOARD
===============================================================================

At the very end of the pipeline sits a dashboard for the business users, built
with STREAMLIT.

WHAT IS STREAMLIT?
Streamlit is a tool for building simple, interactive web dashboards using
Python code. This project uses "Streamlit in Snowflake", meaning the dashboard
runs directly inside Snowflake, right next to the data.

The dashboard reads from the GOLD-layer KPI VIEWS and displays:
   - Overall performance (total revenue, total orders, max order value).
   - Year-by-year KPIs with comparison to the previous year (up/down arrows).
   - Monthly revenue trends as bar and line charts.
   - A ranked table of the top restaurants for a chosen month.

The user can pick a year and a month from dropdown menus, and every number and
chart updates instantly. This is the payoff of the whole project: messy raw
files have become clean, trustworthy, instantly explorable business insight.


===============================================================================
PART 5 — SIDE-BY-SIDE SUMMARY OF THE TWO APPROACHES
===============================================================================

SAME in both approaches:
   - The destination: a Snowflake data warehouse.
   - The medallion architecture: Bronze (stage) → Silver (clean) → Gold
     (consumption).
   - The star schema: fact table + dimensions, with SCD Type 2 history.
   - The final Streamlit dashboard.

DIFFERENT:

   HOW INFRASTRUCTURE IS CREATED
      Manual:      by hand, clicking and running SQL in Snowflake.
      Automated:   defined in code and built by Terraform (Infrastructure as
                   Code), across both Snowflake and Azure.

   WHERE RAW FILES LIVE / HOW THEY ARE LOADED
      Manual:      files uploaded by hand into Snowflake's internal stage.
      Automated:   files copied by Azure Data Factory into Azure cloud storage
                   (a data lake), then read by Snowflake via a secure external
                   stage.

   HOW TRANSFORMATIONS RUN
      Manual:      SQL scripts run one by one, by hand, in the correct order.
      Automated:   dbt models run automatically in dependency order.

   HOW HISTORY (SCD TYPE 2) IS HANDLED
      Manual:      long hand-written MERGE statements (100+ lines each).
      Automated:   dbt snapshots (about 10 lines each).

   DATA QUALITY CHECKS
      Manual:      none (you hope the data is correct).
      Automated:   dbt tests run automatically every time.

   DOCUMENTATION
      Manual:      none.
      Automated:   dbt generates docs and a visual lineage graph automatically.

   AUTOMATION / SCHEDULING
      Manual:      nothing is automatic; a person runs everything.
      Automated:   Azure Data Factory runs the whole chain (copy → load →
                   transform) automatically every hour via a schedule trigger.

WHY KEEP BOTH?
The manual version proves deep understanding of the fundamentals — you can see
and control every step, and you understand exactly WHAT each tool automates.
The automated version proves the ability to apply professional, production-grade
tooling. Together they tell a strong story: "I first built this by hand to
master the concepts, then re-engineered it into a fully automated, tested,
documented, multi-cloud pipeline." That progression is exactly what a strong
data engineer demonstrates.
